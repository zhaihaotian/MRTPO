TL;DR GDPO tells a multi-reward learner which rewards a response earned; MRTPO also tells it which tokens earned each of them. For each reward, the policy replays its own response with and without that reward's verifier information, and the per-token Jensen–Shannon distance between the two next-token distributions decides where that reward's advantage goes. No auxiliary model, no token labels, no extra generation.

01 · The problem

🎯 One wrong token, and the penalty lands everywhere

Language models are increasingly trained against several verifiable rewards at once: the correctness and the format of a tool call, or the individual constraints of a complex instruction. GDPO normalizes each reward separately, so different reward combinations keep distinct advantages. But in GRPO, GDPO and SAW, every token of a response shares one advantage.

A verifier checks only a few positions. The penalty for one wrong token is spread over the whole response, where it can be outweighed by the credit other rewards put on the same tokens.

02 · Method

💡 Let each verifier's information point to its tokens

MRTPO assigns the advantage of each reward to the tokens relevant to it, using the information its verifier checks.

  1. Write each verifier's information as a text block

    \(Z_k\) is what reward \(k\) checks: the format rule, the response's own SQLite error, the reference query, or one constraint of the instruction. \(P_{\text{all}} = P_0 \oplus\) all blocks; \(P_{\setminus k}\) leaves out \(Z_k\). When the information is already in the prompt (instruction constraints), \(P_{\text{all}}\) is the prompt and \(P_{\setminus k}\) removes one constraint. Sampling still uses \(P_0\).

  2. Replay the response under both contexts

    The sampling policy reads its own response once under each context, one forward pass per context, with no new generation. At every token \(t\), the Jensen–Shannon distance \(q_{k,t}\) between the two next-token distributions measures how relevant that token is to reward \(k\).

  3. Move each reward's advantage to its tokens

    The distances become per-token weights, and each token's advantage is the weighted sum over rewards. The weights average to 1 per response, so every response keeps its GDPO credit; only the placement changes.

\[ q_{k,t}=\sqrt{\frac{\mathrm{JS}\!\left(p^{\text{all}}_t \,\middle\|\, p^{\setminus k}_t\right)}{\ln 2}} \qquad w_{k,t}=(1-\beta)+\beta\,\frac{q_{k,t}}{\bar q_k} \qquad S_t=\sum_k A_k\, w_{k,t} \]
\(A_k\): GDPO's group-normalized advantage of reward \(k\) for the response; \(\bar q_k\): mean of \(q_{k,t}\) over the response; \(\beta = 0.5\). \(S_t\) is then divided by GDPO's batch standard deviation.

What changes compared with GDPO

MethodWhat changes in the GDPO stepToken advantage \(S_t^{(j)}\)
GDPOnothing; the per-reward advantages are summed\(\sum_k A_k^{(j)}\)for all \(t\)
SAWeach reward is weighted by its coefficient of variation in the batch\(\sum_k \lambda_k A_k^{(j)}\)for all \(t\)
DARArewards that vary in fewer groups get a larger, capped weight on their positive advantages\(\sum_k \bigl(A_k^{(j)} + (\lambda_k - 1)[A_k^{(j)}]_+\bigr)\)for all \(t\)
DVAOeach reward is weighted by its standard deviation within the group, normalized across rewards\(\sum_k \lambda_k A_k^{(j)}\)for all \(t\)
SA-MRPOeach reward is discounted by how saturated it is in the batch\(\sum_k \lambda_k A_k^{(j)}\)for all \(t\)
GD²POresponses whose per-reward advantages disagree in sign are dropped, and each prompt is scaled by its share of kept responses\(\kappa\,\delta^{(j)} \sum_k A_k^{(j)}\)for all \(t\)
RVPOthe rewards are combined by a soft minimum, which penalizes their variance\(\operatorname{softmin}_k A_k^{(j)}\)for all \(t\)
MRTPOeach reward's advantage is assigned to tokens by relevance\(\sum_k A_k^{(j)}\, w_{k,t}\)

The other methods act on the response, so every token of a response gets the same advantage. MRTPO sets a weight per reward and token and can be combined with them.

GDPO step
  1. Sample a group of responses from \(P_0\) and score every reward
  2. Normalize each reward within the group: \(A_k\)
  3. Sum the rewards: \(S=\sum_k A_k\), the same on every token
  4. Divide by the batch standard deviation and update the policy
MRTPO step
  1. Sample a group of responses from \(P_0\) and score every reward
  2. Normalize each reward within the group: \(A_k\)
  3. For each reward \(k\), find its relevant tokens: replay \(y\) after \(P_{\text{all}}\) and after \(P_{\setminus k}\); \(q_{k,t}\) = JS distance of the two predictions; \(w_{k,t}=(1-\beta)+\beta\,q_{k,t}/\bar q_k\)
  4. Sum the rewards on each token: \(S_t=\sum_k A_k\, w_{k,t}\)
  5. Divide by the batch standard deviation and update the policy
CostA training step takes 10–20% longer than GDPO. Replay only runs for rewards that vary within the group, so only 12–21% of response–reward pairs need one.

05 · Analysis

🔍 Where the credit goes

Each reward's distance concentrates on a small part of the response. In text-to-SQL, 80% of a reward's distance falls on 26–29% of the tokens; in tool calling, on 13–15%. In instruction following, an end-phrase constraint puts 40% of its distance on 4% of the tokens: the phrase itself.

06 · Practice

🧪 Using MRTPO on your own task

MRTPO needs two things from a task:

1 · Rewards

A vector of rewards, each scored by its own verifier, as in GDPO.

2 · Verifier blocks

For every reward, a text block that carries the information its verifier uses. The two replay contexts differ only in this block, so the block decides which tokens receive the reward's advantage.

Building the two contexts

For each reward \(k\) the replay compares \(P_{\text{all}}\), which contains the blocks of all rewards, with \(P_{\setminus k}\), the same context with block \(k\) removed.

The prompt does not show it

Tool calling, text-to-SQL. The verifier holds information the policy never sees while sampling: the reference calls, the reference query, the response's own SQLite error. Write each piece as a block and append the blocks to the rollout prompt \(P_0\): \(P_{\text{all}} = P_0\) + all blocks, \(P_{\setminus k} = P_0\) + all blocks except block \(k\). The rollout itself still uses \(P_0\).

The prompt already shows it

Instruction following. Every constraint the verifiers check is part of the instruction, so the rollout prompt is already \(P_{\text{all}}\). Nothing is added; \(P_{\setminus k}\) is the rollout prompt with constraint \(k\) deleted.

Writing a block

  • One reward, one block. Never merge several constraints, rubric items or verifiers into one.
  • Write the information itself, specific to this example. Build every block by code from the example's label or the verifier's own output; a generic requirement ("the query must execute") carries no information.
  • Write it as a plain statement, like the rest of the prompt. No instructions to the model, headings, labels, or words about training, replay or scoring.
  • Use only this response's own feedback. If there is none, the block is empty; never invent one.
  • Write references in the form the policy is asked to produce, with the same tags, code fences and argument types.
  • Keep the prompt, the rewards and the blocks consistent, and replay the rollout prompt and the response exactly as sampled.
Which rewards fit

MRTPO helps when a reward's information, written as text, changes what the policy would write at the positions its verifier reads: a tool name and its arguments, a table or column, a required phrase. In math reasoning, the answer block points only at the last number, and a length limit is not decided by particular tokens. We did not evaluate MRTPO on math answer and length rewards or on GDPO's coding rewards.

Hyperparameters

β = 0.5 works in all our settings and is a good default; some tasks may prefer a smaller β. The reallocation bound keeps long training runs stable, so we use it in all settings. For short training, MRTPO without the bound also works well (--no-reallocation-bound).
